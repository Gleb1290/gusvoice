# gpu-path-bench — замер «кадр внутри видеокарты» (#207, шаг 4.0)

Отдельная программа, не приложение. Снимает монитор через DXGI и кодирует его тремя слоями NVENC с
теми же настройками, что показ экрана в GusVoice, но никуда не отправляет. Нужна, чтобы до переделки
приложения узнать в цифрах, что даст путь кадра внутри видеокарты — на пустом столе и под игрой.

Режимы — два основных и два для разбора, откуда у игры рывки:
- `capture` — только захват DXGI (взять и отпустить кадр), без копий и кодирования;
- `idle` — ни захвата, ни кодирования;
- `--engines 0` в любом режиме — не опрашивать раз в секунду счётчики `GPU Engine`;
- `--shared` в режиме `gpu` — устройство как в приложении: у кодировщика своё D3D11-устройство, кадр
  приходит общей текстурой (NT-хэндл + keyed mutex). 26.09 работает так же, как одно устройство.

Захват — `DuplicateOutput1` с BGRA, как в приложении: у 10-битного вывода Windows 11 складывает стол
в FP16 даже без HDR.

Основные:

| | `cpu` — как сейчас в приложении | `gpu` — кадр не покидает видеокарту |
|---|---|---|
| забор кадра | копия в staging → `Map` ждёт видеокарту → копия в оперативку | копия в свою текстуру внутри видеопамяти |
| перевод цвета и слои | libyuv на процессоре (тот же, что в приложении: из prebuilt libwebrtc) | видеопроцессор D3D11: BGRA→NV12 с уменьшением прямо во вход NVENC |
| в видеокарту | CUDA грузит каждый слой обратно | не нужно |
| NVENC | CUDA-сессия (`NvEncoderCuda`, как в приложении) | D3D11-сессия (`nvenc_d3d11.h`, без CUDA) |

Повторяет из приложения: лестницу слоёв `share_layer_presets`, P4 + ULL + CBR, бесконечный GOP,
синхронное кодирование, пейсинг по дедлайну, `CU_CTX_SCHED_BLOCKING_SYNC`.

Не повторяет:
- курсор (DXGI отдаёт его отдельно);
- сеть, dynacast, превью;
- **два потока.** В приложении забор+перевод и кодирование идут в разных потоках, здесь в одном.
  Поэтому «опоздавшие тики» в режиме `cpu` хуже, чем в приложении. Сравнивать процессор, стадии и
  движки видеокарты, а не опоздания;
- HDR-стол и ноутбуки, где монитор подключён к встроенной графике (Optimus), — замер откажется.

## Сборка

```powershell
$env:GV_CUDA_DIR = 'S:/gv-ci-cuda/cuda_cudart-windows-x86_64-12.6.77-archive'   # как в CI
pwsh -File apps/desktop/tools/gpu-path-bench/build.ps1
```

Нужен prebuilt libwebrtc от LiveKit: он появляется после любой `cargo build` десктопа, скрипт ищет его
в `src-tauri/target` сам (или `-WebrtcDir`). Не собирать при запущенной игре: `cl.exe` на этой машине с
игрой падает.

## Быстрый прогон

```powershell
build\gpu-path-bench.exe --list                       # номера мониторов
build\gpu-path-bench.exe --mode gpu --seconds 20
build\gpu-path-bench.exe --mode cpu --seconds 20 --max 2560x1440
```

Раз в секунду — строка с кадрами и битрейтом слоёв, стадиями (сред/макс, мс), процессором и движками
видеокарты нашего процесса. В конце — итог без первых 2 с и строка JSON (`--json файл` — то же в файл).

## Протокол под игрой

1. PresentMon 2.6 (кадры игры): `PresentMon-2.6.0-x64.exe` в `C:\pm\` — откуда и как, в
   `docs/streaming-playbook/04-app-footprint-and-measuring.md`, раздел B3. Без него протокол всё равно
   идёт, но кадров игры не будет.
2. GusVoice экран не показывает (лучше закрыть). Игра запущена, персонаж стоит в одной сцене.
3. `pwsh -File run-protocol.ps1 -Game valheim.exe -Monitor 0 -Max 2560x1440` — и переключиться в игру
   за 15 секунд. Пять фаз по 90 с: без показа, cpu, gpu, cpu, gpu (~9 минут). Ничего не трогать.
   `-Plan isolate` — шесть фаз, чтобы найти источник рывков: без показа, только опрос, gpu без опроса,
   только захват, gpu с опросом, снова без показа.
4. В конце — таблицы PresentMon и замера. Всё лежит в `C:\pm\bench-<дата>`.

## Как читать

- **Процессор** (`CpuCore`, % одного ядра) и **стадии** — цена показа для машины.
- **`OurCopy`** — копирующий движок видеокарты: им идут забор в оперативку и загрузка обратно. Игры
  тоже им пользуются (подгрузка текстур).
- **`Our3D`** — наш перевод на видеокарте; он встаёт в одну очередь с игрой.
- **PresentMon по фазам**: средние и 1 % худших кадров игры, `GPUWait`/`CPUWait` — кто кого ждёт.
- **«наш D3D11 на видеокарте»** (только `gpu`) — время от начала до конца нашей копии и перевода на
  шкале видеокарты. Под игрой туда попадает и её работа между нашими командами.

| фаза | к/с игры | 1 % худших | рывков (`Hitches2x` из pm-summary) | показ, к/с | процессор показа, % ядра |
|---|---|---|---|---|---|

| cpu | 142,0 / 142,2 | 82,8 / 81,1 | 60 / 64 | 57,1 / 56,7 | 60 / 61 |
| gpu | 141,2 / 142,4 | 79,8 / 82,5 | 53 / 59 | 60,0 / 60,0 | 4,9 / 4,4 |

- **Показу путь через видеокарту помогает сильно:** ровные 60 к/с вместо 57, процессор в 12 раз меньше.
- **Игре — никак:** между cpu и gpu разницы нет. Оба пути одинаково добавляют ~55–60 рывков за 90 с.
- Рывок = долгий кадр игры по ПРОЦЕССОРУ (CPUBusy 14–22 мс при обычных 7), видеокарта ни при чём.
  Промежутки между рывками часто ровно 1, 2, 3 с: срабатывает что-то ежесекундное. Подозреваемый —
  ежесекундный опрос счётчиков `GPU Engine` самим замером (у приложения тот же опрос раз в 15 с при
  показе). Проверяется планом `-Plan isolate`: фазы «только опрос», «gpu без опроса», «только захват».

**Разбор рывков, `-Plan isolate`** (26.09, та же сцена, фазы по 60 с, PresentMon пишет ~54 с):

| фаза | 1 % худших | `Hitches2x` | кадров > 2× медианы | p99,9 кадра, мс |
|---|---|---|---|---|
| без показа (в начале) | 99,6 | 6 | 6 | 13,1 |
| только опрос `GPU Engine` | 98,5 | 4 | 4 | 13,3 |
| gpu без опроса | 92,0 | 20 | 16 | 15,1 |
| только захват DXGI, без опроса | 96,0 | 13 | 10 | 13,9 |
| gpu с опросом | 96,6 | 22 | 11 | 14,1 |
| без показа (в конце) | 99,1 | 1 | 1 | 12,4 |

- ❌ **Опрос счётчиков не виноват:** «только опрос» = «без показа».
- **Сам захват DXGI уже чуть бьёт игру** (10 долгих кадров против 1–6), хотя наш процесс в этой фазе
  почти ничего не делает (0,4 % ядра, ноль работы на видеокарте). Кодирование добавляет ещё немного.
- **На долгих кадрах игра НЕ ждёт в Present** (`MsInPresentAPI` 0,05 мс, как у обычных): все 14–16 мс —
  её собственная работа на процессоре. Это похоже на вытеснение потока игры, а не на ожидание видеокарты
  или синхронизации. Кандидат, НЕ ПОДТВЕРЖДЁННЫЙ: DWM с повышенным приоритетом делает лишнюю работу на
  каждый кадр для захвата.
- ⚠️ **Разброс между прогонами большой.** Тот же режим «gpu с опросом» дал 49–51 долгий кадр за 84 с в
  первом прогоне и 11 за 54 с во втором: втрое чаще при тех же настройках. Точные доли по одному прогону
  не выводить. Устойчиво только качественное: путь кадра (cpu/gpu) игре в этой сцене безразличен, а
  основная цена для игры — в самом захвате.

**Вывод для шага 4:** путь внутри видеокарты окупается для ПОКАЗА (ровные 60 к/с, процессор в 12 раз
меньше; важнее всего слабым машинам), но рывки игры в сцене с упором в процессор он не лечит. Не проверен
случай «видеокарта в упоре» — там нынешний путь делит с игрой копирующий движок и ждёт её очереди при
чтении кадра. Следующий замер — тяжёлая игра (Crimson Desert) планом `compare`.

**Под Crimson Desert — видеокарта в упоре** (26.09, `C:\pm\bench-20260926-0031`, 3D игры 93–95 %, фазы
по 90 с). По кадрам видна генерация кадров: медиана между кадрами на экране 0,5 мс, CPUBusy 0,4 мс.
Поэтому процессорные и видеокарточные метрики PresentMon на кадр тут не читаются, смотреть к/с на экране,
рывки и хвост времени кадра.

| фаза | к/с игры | рывков (`Hitches2x`) | p99,9 кадра, мс | показ, к/с | процессор показа, % ядра |
|---|---|---|---|---|---|
| без показа | 151,4 | 0 | 39,8 | — | — |
| cpu | 139,4 / 139,2 | 18 / 15 | 44,2 / 44,6 | 31,8 / 31,5 | 42,7 / 42,0 |
| gpu | 141,3 / 141,6 | 2 / 0 | 43,2 / 43,1 | 45,3 / 45,3 | 3,1 / 3,2 |

- ✅ **В упоре видеокарты путь через неё помогает и игре:** рывки 15–18 → 0–2, в обоих повторах; к/с
  на 2 выше (−6,5 % от игры без показа против −8 %).
- ✅ **Показ: 45 к/с вместо 31,5** (+43 %) при процессоре в 13 раз меньше. У нынешнего пути `Map` ждёт
  видеокарту 32 мс (p95) — чтение кадра стоит в очереди за игрой.
- 🔴 **60 к/с показа не достигает ни один путь.** Кодирование ждёт 36 мс (p95) в обоих: наш перевод и
  NVENC встают в очередь видеокарты за игрой, а поток ждёт каждый кадр (синхронно, как в приложении).
  Это прогноз плана «очередь остаётся», подтверждённый замером. Следующий опыт — конвейер: несколько
  кадров в работе одновременно (асинхронный NVENC, задержка выхода 1–2 кадра), чтобы ожидание очереди
  стоило задержки, а не частоты кадров.

**Конвейер NVENC, `-Plan pipeline`** (26.09, Crimson Desert, `C:\pm\bench-20260926-0048`, фазы по 75 с;
`--depth N` — подача кадра ждёт готовности кадра на N раньше):

| фаза | показ, к/с | опоздавших тиков | задержка кадра p50 / p95, мс | к/с игры | рывков |
|---|---|---|---|---|---|
| без показа | — | — | — | 143,0 | 0 |
| конвейер 0 (как сейчас) | 49,9 / 50,6 | ~1000 | 3,3 / 26 | 134,1 / 156,7* | 0 / 1 |
| конвейер 1 | 59,9 / 59,9 | ~70 | 17,1 / 30 | 135,2 / 135,1 | 11 / 2 |
| конвейер 2 | 60,0 / 60,0 | 0 | 33,6 / 34,1 | 156,8* / 134,5 | 0 / 2 |

\* Фазы 4 и 5 шли подряд, и сцена в них сама стала легче: 157 к/с при любой глубине, больше, чем без
показа. Сравнивать к/с игры только внутри одной сцены: там все глубины дают 134–135 к/с (−6 % от игры
без показа), конвейер игре не мешает. Рывки — на уровне шума.

- ✅ **Конвейер снимает потолок показа:** 50 → 60 к/с в упоре видеокарты, процессор 3–6 % ядра.
- Цена — задержка. Здесь её дискретизирует шаг цикла: пакет забирается на следующем тике, поэтому
  глубина 1 ≈ +17 мс, глубина 2 ≈ +33 мс. В приложении готовый кадр надо отдавать из отдельного потока,
  ждущего события NVENC (модель из руководства NVIDIA). Тогда задержка равна реальному времени на
  видеокарте, а не шагу цикла.
- **Выбор для 4.1: глубина 1.** Это 59,9 к/с при медиане +17 мс; глубина 2 добавляет ещё кадр ради
  последних 0,1 к/с.

**Итог шага 4.0:** путь внутри видеокарты делать. В упоре видеокарты он лечит и показ, и рывки игры, в
упоре процессора — только показ. Для 4.1 обязательны:
- `Flush()` перед кодированием;
- конвейер глубины 1;
- выдача готовых кадров из отдельного потока (`OnEncodedImage` libwebrtc можно звать не из потока
  `Encode`: так работают аппаратные кодировщики Android — проверить при реализации).

⚠️ 4.1 без 4.2 пользы не даёт: кодировщику нечего принимать, пока захват отдаёт кадры в оперативке.
Выпускать 4.1 и 4.2 одним релизом за переключателем.

🔴 **Урок для шага 4.1:** после записи во вход NVENC обязателен `Flush()` контекста D3D11. Без него
метки времени показали, что наш перевод уходит на видеокарту только на СЛЕДУЮЩЕМ тике (разрыв ровно
в один кадр, с `Flush()` — 0,27 мс). То есть NVENC-сессия буфер D3D11 сама не выталкивает, и
кодировщик брал текстуру раньше, чем в неё записан новый кадр. Глазами поток не сравнивал: декодера
на машине нет.
